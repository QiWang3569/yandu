# M3E-small 在燕渡服务器上的试验

2026 年 11 月 21 日。在现有阿里云 ECS 上使用单线程 ONNX Runtime 实测了 M3E-small 动态 INT8 版。上轮 16 条笔记本歧义查询中，原始浮点版前三覆盖 16/16，这次把它作为候选检索器参加新题测试。M3E-small 原始权重约 96 MB，模型输出 512 维。[上轮选型](../2026-11-21-local-embeddings/README.md) · [模型发布页](https://huggingface.co/moka-ai/m3e-small)

## 服务器开销

机器为 x86-64、2 个逻辑 CPU、3627 MiB 内存，开始时可用 2537 MiB。临时目录中实测，在已运行线上服务的主机上单进程、低调度优先级、串行处理合成查询。模型文件 22.8 MiB，进程峰值 RSS 112.7 MiB。引擎和分词器初始化 119.04 毫秒（不含 Python 和库导入）。商品向量预先计算，372 次预热后的查询，P50 为 4.38 毫秒，P95 为 7.07 毫秒。计时从分词开始，到对内存中的商品向量完成相似度排序结束。最大目录只有 57 件商品，未测并发、在线意图解析、数据库查询或 HTTP 往返。[服务器原始结果](server.json)

转换使用上轮相同提交的权重和分词器，保留按 attention mask 求均值及归一化。46 段新测试文本上，浮点 ONNX 与原始模型向量余弦相似度最低超过 0.99999，INT8 最低 0.9887，平均 0.9922。当前数据库远程向量列为 1536 维，若接入服务，512 维商品向量需要单独索引并重新编码商品。[转换验证](export-check.json) · [模型转换](export_model.py) · [现有向量字段](../../../backend/app/models.py)

## 现有规则为什么在原回归上高分

开发记录显示，团队反复查看同一批用例的漏匹配与误匹配，然后改商品主体与配件判断、否定处理、属性和价格规则，再回放相同记录。例如对 MacBook、充电器和支架的误返补了主体判断，还按项目确认的价格段调整了“两百多”的代码和测试标注。[第一轮记录](../../../docs/SMART_SEARCH_REGRESSION_20261121.md) · [第二轮记录](../../../docs/SMART_SEARCH_ROUND2_20261121.md) · [商品匹配词表](../2026-11-21-reproduction/source/backend/app/smart_terms.py)

本次实际从 Git 提交 202fb75 提取旧后端，与当前工作区后端在相同商品、标准答案和本地解析模式下重跑。原回归 74 条有货查询首位从 48 升至 74。连返回集合也正确的从 35/78 升至 78/78。剔除后增、修改的用例，仅看历史 JSON 与现在完全相同的有货查询，首位仍从 47/69 升至 69/69。同样的规则改动在新题上从 5/24 升至 8/24，在上轮笔记本专项上从 3/16 变为 2/16。数据支持开发集适配，也显示部分改动能迁移到新商品。商品和问法同时改变，无法精确拆出两者各自的贡献。

服务器向量单独检索在原有货查询首位为 52/74，笔记本专项为 13/16，前三分别为 69/74 和 16/16。新增这批用例更适合检验新措辞，原回归更适合防止已修正的业务规则退化。[全部指标和逐条商品名](summary.json)

## 大模型选品与排序的耗时边界

指标为**评测客户端单次远程选品与排序调用耗时（P50）**。两组都使用 OpenLux DeepSeek Flash，输入同一批 28 条查询，每条独立调用一次，最多并发 3 条。以下两组均提供售价，所有请求首次成功。

| 传给模型的商品 | 每次平均输入 token | 调用耗时 P50 |
| --- | ---: | ---: |
| M3E 已召回的 5 件 | 301 | 4.96 秒 |
| 完整目录的 18 件 | 895 | 7.08 秒 |

1. **计时前**，脚本读取商品及已有的 M3E 候选记录，打乱候选顺序，分配临时编号，把用户原话、商品标题、描述、标签和售价拼成消息。任务在线程池里等待的时间也在计时区间之外。
2. **计时开始**于客户端准备调用 `client.post`。区间覆盖 HTTP 请求体编码与发送、网络往返、平台处理（含可能的排队）、模型读取需求和商品、判断哪些符合、按推荐顺序生成最多三个编号或空列表，以及客户端接收完整响应。这些判断和排序在同一次请求里完成。
3. **计时结束**于客户端解析响应和模型输出的 JSON，检查生成结束状态、列表长度、编号合法性及重复项，把临时编号还原为商品 ID 并取出用量信息之后。后续商品名映射、标准答案评分和写报告均在区间之外。

脚本只记录上述区间的总时长，没有单独记录网络、平台排队、模型纯推理或首个 token 的耗时。两种方案分轮运行，约 2.12 秒是这两组中位数之差，无法全部归因于候选数量。M3E 的 4.38 **毫秒**是另一次服务器实验的向量检索 P50。此次大模型评测读取此前的召回结果，未测从用户提交搜索到页面展示的端到端耗时。[计时实现](llm_ranking.py) · [五件候选的逐次耗时](m3e-llm-ranking.json) · [全目录逐次耗时](llm-ranking.json)

## 加快五件候选的最终排序

固定同一批 M3E 前五候选、售价、展示顺序和 28 条查询，在 OpenLux 上交替调用以下模型。并发上限为 3。P50 取中位数，P95 取 28 条耗时升序的第 27 条。计时覆盖发出请求至校验完成，包括失败重试和等待，不含候选准备或本地任务队列。

| 排序模型 | P50 | P95 | 有货首位 | 无货正确返回空 | 整份清单正确 |
| --- | ---: | ---: | ---: | ---: | ---: |
| DeepSeek V4.1 Flash | 3.38 秒 | 5.89 秒 | 24/24 | 4/4 | 28/28 |
| GPT-4.1 nano | 1.60 秒 | 2.59 秒 | 23/24 | 4/4 | 24/28 |
| GPT-4.1 nano，补充选品约束后单独复测 | 1.29 秒 | 2.41 秒 | 23/24 | 4/4 | 27/28 |

同轮两种模型均首次成功，nano 的中位耗时少 53%。在相同题目上调整提示词后，nano 的额外推荐消失，仍把“想收副普通耳麦，带主动降噪的就算了”误判为无货。补充约束版的耗时来自单独一轮。Gemini 2.5 Flash-Lite 的 28 条中有 23 条最终超时或输出未通过校验。上述结果来自开发集，线上并发和用户端耗时另计。[交替调用明细](m3e-latency-trial.json) · [选品约束复测](m3e-nano-check.json)

## 复现

在仓库根目录，以项目虚拟环境运行 prepare.py 的 old、current 两种模式，使用带有 Sentence Transformers 的 Python 运行 float 模式并传入上轮固定版本的 M3E-small 权重目录。input 模式只生成无标签查询和商品文本。export_model.py 导出模型，Linux 环境运行 server_bench.py 时将 model.onnx、tokenizer.json 和 server-embedding-input.json 置于同一目录。本次使用 ONNX Runtime 1.22.1、tokenizers 0.21.4、NumPy 2.2.6。在该目录生成 server.json。将结果交给 score.py 与固定标准答案比对。[准备输入与规则对照](prepare.py) · [服务器计时代码](server_bench.py) · [评分代码](score.py)
