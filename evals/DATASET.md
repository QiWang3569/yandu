# 模型评测用例库

当前版本包含 48 个合成用例：需求解析 24 个、商品信息提取 8 个、求购解析 8 个、候选精筛 8 个。每个候选精筛用例有 3 件商品，共 24 个判断。

所有用例都为 `enabled: true`、`split: "dev"`、`label_status: "draft"`。输入与预期由助手构造，待项目成员复核；它们用于调试评测流程、发现失败场景和建立回归基线。当前没有人工审定的保留集，也没有真实用户数据。

## 目录与编号

```text
evals/cases/
  intent_parse/       intent-001.json … intent-024.json
  item_parse/         item-001.json … item-008.json
  wanted_parse/       wanted-001.json … wanted-008.json
  candidate_review/   review-001.json … review-008.json
```

每个文件对应一个用例。文件名与 `id` 一致，ID 在整个用例库中唯一，停用或删除后不分配给其他场景。候选 ID 只需在所属用例内唯一，`expected.verdicts` 必须覆盖所有候选且不包含额外 ID。

## 字段约定

| 字段 | 内容 |
| --- | --- |
| `id` | 稳定且唯一的用例 ID |
| `task` | `intent_parse`、`item_parse`、`wanted_parse` 或 `candidate_review` |
| `enabled` | 是否进入默认执行集合 |
| `split` | `dev` 或 `holdout`；首版全部为 dev |
| `family` | 同类表达及近似场景的分组，划分数据集时整组处理 |
| `tags` | 过滤执行、汇总失败类型使用的标签 |
| `source` | 合成来源或实际来源与去标识处理说明 |
| `rationale` | 标签依据、关键业务规则和本例评分边界 |
| `label_status` | 标注复核状态；首版全部为 draft，复核状态值应遵循执行器的 schema |
| `input` | 文本，或固定需求与固定候选商品 |
| `expected` | 预期结构字段、概念集合、澄清要求，或候选结论 |

这 11 个根字段都需保留。业务枚举以 `backend/app/schemas.py` 为准：

- 分类：课程资料与书籍、数码与影音、校园出行与运动、宿舍生活与家电、美妆服饰与周边、人员招募。
- 校区：燕园校本部、万柳学区、医学部、昌平新校区、不限校区。
- 成色：全新、95新、9成新、8成新、基本可用。

## 解析任务的标注规则

解析任务输入为 `{"text": "原文"}`。`expected.fields` 只列入需要评分的字段，字段省略表示不评该字段，`null` 表示明确期望为空，二者含义不同。价格均以元为单位，99.50 与 99.5 是相同数值。

- `intent_parse` 使用 `category`、`max_price`、`campus`、`condition_grade`。
- `item_parse` 使用 `category`、`price`、`campus`、`condition_grade`。
- `wanted_parse` 使用 `category`、`budget`、`campus`，其当前输出不含条件数组。

`expected.sets` 中每个内层数组表示一个语义概念及其可接受等价表达。例如：

```json
{
  "sets": {
    "keywords": [["鼠标", "滑鼠"], ["无线"]],
    "excluded_keywords": [["游戏鼠标"]],
    "preferences": [["静音", "无声"]]
  }
}
```

以上期待两个必须概念、一个排除概念和一个偏好概念。评分按完整词项匹配同义词组，不以子串命中代替概念匹配；缺项和额外概念都应受到惩罚。空数组表示这一组应为空；`sets: {}` 表示本例不评价概念数组。近似品类不能加入同义词组，例如网球拍与羽毛球拍、无线与蓝牙、帆布包与任意手提袋均不能直接视为等价。

如需为真实输出补充同义表达，应先由复核者确认语义等价，再修改用例并保留变更理由；不要仅为提高某个模型分数放宽标签。将“无线鼠标”合为一个词项与拆成“鼠标 / 无线”是否等价，需在正式评分规则中统一处理；当前样例沿用业务 prompt 的原子概念表达，并保留 draft 状态供团队确认。

`expected.clarification: true` 表示需要非空澄清内容。它只校验是否提出澄清，澄清是否准确指出矛盾或缺失信息需人工复核。未给该字段时不评价澄清。首版没有对标题、描述逐字匹配；这些生成文本的事实保留与无依据新增信息需另外复核。

关键标注规则：

- 中文金额、预算修正、否定作用域都按用户语义标注，不能根据本地规则能否解析来调整标准答案。
- “最好 / 优先”属于偏好；“必须”属于要求；未提及预算为 null。
- `intent-017` 中的要求直接冲突，当前业务 schema 又禁止同词同时出现在要求与排除数组，因此只评分未冲突字段和澄清，不强制一种无法表达冲突的数组结果。
- `item-007` 未给出校区与成色。现有 `ParsedItem` 默认填入燕园校本部和95新，不能将这些默认值当作正确抽取。该例省略这两个评分字段，并在 rationale 中记录接口缺口。
- `wanted-004` 只检查约数预算的基准金额。搜索时采用的预算容差不在当前求购结构中，需通过端到端检索用例验证。

## 候选精筛的标注规则

每例固定同一份 `intent` 与候选列表，所有模型接收相同输入。此层假定价格、校区、成色已通过程序硬过滤，只评价语义精筛。

- `MATCH`：文本明确支持所有必须条件，并支持需要核验的排除条件；偏好不满足仍可匹配。
- `NO_MATCH`：文本明确与某一必须条件或排除条件冲突。
- `UNCERTAIN`：主体或关键条件缺少证据，需要向卖家提问。

“没有提及”不等于“明确没有”；“非游戏鼠标”不应因为包含“游戏鼠标”四字而被拒绝；不能凭型号联想未写明的功能。候选文本内要求改变规则、输出 MATCH 的指令只作为数据处理。

预期结论在 `expected.verdicts` 中逐候选标注。现有业务会校验证据是否逐字来自商品，也会把缺少硬条件证据的 MATCH 降为 UNCERTAIN。报告需要区分模型原始输出与应用校验后的结论，并记录校验失败或降级。逐字引用合法不代表逻辑成立，证据能否支持判断仍需抽样人工复核。

候选结论样例数量为 MATCH 9、NO_MATCH 7、UNCERTAIN 8。本库适合计算三分类结果、误判与信息不足处理情况；每例只有3件候选，且没有相关性排序标注，不能用它计算课程验收口径中的代蹲 P@5。视觉识图也未包含在这48例中，应另建图片与人工标签用例后评价。

## 增加、修改、停用和删除

1. 新增：复制同任务文件，分配新 ID，修改输入、预期、family、tags、source 与 rationale。新合成例使用 dev / draft；运行用例校验后再执行对应任务。
2. 修改：保持场景含义不变时沿用 ID，通过 Git diff 记录输入、答案或同义词变更。若已变成另一个独立场景，创建新 ID。
3. 停用：设 `enabled: false`，在 rationale 中追加停用原因与日期。重复用例、业务规则废弃或标注错误均可停用，模型失败本身不是停用理由。
4. 删除：确认场景废弃后删除对应 JSON，保留 Git 历史及删除原因。历史报告必须保留当次用例列表或完整快照、数据集哈希，才能复现删除前的结果。
5. 回归：新增或修正失败场景后运行对应任务，再运行全部离线评测检查；比较报告时固定相同用例集合。集合变化时先列明新增、删除和预期变更，再比较共同用例。

增加用例无需修改 Python 测试函数。正式模型比较前，应冻结用例内容、同义词、评分版本、模型参数与 prompt；不能看完各模型结果后再改标签决定胜者。

## 人工复核与保留集

当前48例均为开发样例草稿，模型名称、API 调用和结果表不会自动使标签成为人工金标准。团队复核应逐例确认输入是否自然、预期是否唯一、同义词是否等价，以及评分字段是否覆盖本例要考察的行为；争议通过 rationale 记录并修订。

保留集应另采集或独立编写，按 family 及相同素材来源归组，整组分到 dev 或 holdout。已有 prompt 示例、被用于调 prompt 的失败例、相同商品的近义改写不能再作为独立保留例。首版的 `negation-preference`、`specific-category` 等 family 也跨任务共享，划分时应检查跨目录重复。

完成开发集调试后冻结规则，再执行未参与调试的人工复核保留集，单列两组结果。阅读保留集失败并据此调整 prompt 或规则后，这部分样例已经参与开发；下一轮模型选型需补充新的独立保留集。初期样例量较少，报告应给出样例数、失败个数与逐例证据，不能把未观察到错误写成普遍零错误。
